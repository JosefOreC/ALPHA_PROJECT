## 2. Evaluación multidimensional de alternativas

Se evalúan tres alternativas de stack tecnológico conforme a criterios derivados del perfil del proyecto: presupuesto acotado (RES-01), eficiencia energética / eco-diseño (Green Software, ISO 14083), requisitos de rendimiento del algoritmo (RES-04, RES-05), escalabilidad (RES-06) y el perfil técnico del equipo (RES-15).

### 2.1 Tabla comparativa

| Criterio de Evaluación | Alternativa A: MERN (Node/Express + React + MongoDB) | Alternativa B: Python / FastAPI + React + PostgreSQL | Alternativa C: Java Spring Boot + Angular + PostgreSQL |
|---|---|---|---|
| **Curva de aprendizaje** | Baja (JavaScript unificado en frontend y backend) | Media (Python en backend, JavaScript en frontend) | Alta (verboso, fuertemente tipado, ecosistema extenso) |
| **Costo de infraestructura** | Moderado (Node async I/O eficiente) | Bajo (FastAPI asíncrono, bajo consumo RAM) | Alto (mayor consumo de memoria por JVM) |
| **Soporte comunitario** | Masivo / Muy alto | Alto / Crecimiento acelerado en ciencia de datos y backend | Masivo / Corporativo consolidado |
| **Eficiencia energética / Eco-Design** | Media (sin optimización específica de cómputo) | Alta (métricas de cómputo eficientes; Python líder en algoritmos de optimización) | Media-Baja (warm-up JVM prolongado; mayor consumo en arranque) |
| **Capacidad para algoritmos de optimización (VRPTW)** | Baja (JavaScript no tiene bibliotecas nativas maduras para VRPTW) | Alta (bibliotecas OR-Tools, SciPy, NumPy, PuLP disponibles) | Media (implementable pero con mayor costo de desarrollo) |
| **Escalabilidad** | Alta (MongoDB escala horizontalmente; Node async) | Alta (PostgreSQL + arquitectura stateless de FastAPI) | Alta (Spring Boot con microservicios bien establecidos) |
| **Compatibilidad con RES-15** | Parcial (incluye React; no menciona Python ni PostgreSQL) | Total (Python, FastAPI, React, PostgreSQL explícitamente mencionados) | Parcial (Angular en lugar de React/Vue; Java no mencionado) |
| **Integración con mapas (Leaflet / OpenStreetMap)** | Compatible | Compatible | Compatible |

## 3. Justificación Técnica Formal

El equipo seleccionó formalmente la **Alternativa B: Python / FastAPI + React + PostgreSQL** por ser la combinación tecnológica que mejor se alinea con los requerimientos y características del proyecto.

En cuanto a la **escalabilidad**, FastAPI permite desarrollar servicios ligeros y stateless que pueden desplegarse mediante contenedores y escalar horizontalmente en infraestructura cloud conforme aumente la demanda. PostgreSQL, por su parte, proporciona una base de datos robusta y escalable, además de permitir la incorporación de **PostGIS** para la gestión de información geográfica.

Respecto al **perfil técnico del equipo**, la alternativa utiliza tecnologías contempladas en el proyecto, como **Python, FastAPI, React y PostgreSQL**, lo que reduce la curva de aprendizaje y facilita el desarrollo e integración de los diferentes componentes. Además, Python dispone de bibliotecas como **OR-Tools, SciPy, NumPy y PuLP**, adecuadas para implementar los algoritmos de optimización **VRPTW y Green VRP** requeridos.

Finalmente, respecto a los criterios de **bajo consumo energético en la nube**, FastAPI permite implementar un backend ligero y eficiente en el uso de recursos, favoreciendo una infraestructura con menor consumo computacional y permitiendo ajustar los recursos cloud según la demanda.

Por estas razones, la **Alternativa B** ofrece un equilibrio adecuado entre **escalabilidad, capacidades del equipo, eficiencia en el consumo de recursos y capacidad para implementar los algoritmos de optimización requeridos**, por lo que se establece como el stack tecnológico seleccionado para el proyecto.

## 4. Consideraciones adicionales

### Gestión de mapas y datos geográficos

La solución utilizará **React** junto con **Leaflet.js y OpenStreetMap** para la visualización de mapas. Para la gestión de coordenadas y datos geográficos se empleará **PostgreSQL con PostGIS**, facilitando el almacenamiento y consulta de ubicaciones y rutas. La integración con APIs de tráfico será evaluada posteriormente de acuerdo con el AS-03.

### Despliegue e infraestructura cloud

El backend desarrollado con **FastAPI** podrá desplegarse mediante contenedores en una infraestructura cloud, permitiendo escalar los servicios según la demanda y mantener un consumo eficiente de recursos. El proveedor cloud específico será definido durante la planificación de la iteración correspondiente.

### Gestión de base de datos

Se utilizará **PostgreSQL** como sistema gestor de base de datos. Su extensión **PostGIS** permitirá gestionar información geográfica necesaria para el cálculo, almacenamiento y consulta de coordenadas y rutas, apoyando directamente los requerimientos **RF-03 y RF-04**.
