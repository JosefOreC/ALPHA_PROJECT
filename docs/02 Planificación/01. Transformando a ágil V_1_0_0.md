## 2. Justificación del enfoque ágil

El proyecto EcoLogística Lima adopta un **enfoque ágil adaptado (Scrum)** estructurado en cuatro sprints de desarrollo. Esta decisión se sustenta en la incertidumbre técnica inherente al algoritmo VRPTW/Green VRP, la necesidad de retroalimentación continua con operadores reales de DistriRápido S.A.C., y la variabilidad de requisitos dependientes de datos de tráfico y normativa municipal de Lima Este. El enfoque en cascada fue descartado porque varios requisitos (RNF-003, RNF-004, RNF-006) solo pueden validarse contra datos operativos reales obtenidos progresivamente.

## 4. User Stories (Historias de Usuario)

### EP-01 — Gestión de operaciones básicas

---

#### US-001 — Registro de vehículo en flota

**Como** Administrador u Operador  
**Quiero** registrar un nuevo vehículo en el sistema indicando placa, capacidad, tipo de combustible y estado  
**Para** tenerlo disponible para la asignación de rutas de reparto

**Criterios de aceptación (Gherkin / BDD):**

```gherkin
Escenario: Registro exitoso de vehículo nuevo
  DADO que el usuario está autenticado con rol Administrador u Operador
  CUANDO ingresa los datos completos y válidos de un vehículo nuevo (placa, capacidad, tipo de combustible, estado)
  ENTONCES el sistema registra el vehículo, lo asocia a la flota activa y confirma con mensaje de éxito

Escenario: Consulta de vehículos disponibles
  DADO que el usuario tiene rol Operador
  CUANDO consulta la lista de vehículos sin modificar registros
  ENTONCES el sistema muestra el listado actualizado con estado y disponibilidad de cada vehículo

Escenario: Intento de registro con placa duplicada
  DADO que el usuario intenta registrar un vehículo con una placa ya existente
  CUANDO envía el formulario de registro
  ENTONCES el sistema rechaza la operación y despliega: "La placa ingresada ya se encuentra registrada en el sistema"
```

**DoD (Definition of Done):**
- [ ] Endpoint REST documentado en OpenAPI / Swagger
- [ ] Pruebas unitarias con cobertura ≥ 80% sobre el servicio de flota
- [ ] Validación de placa única a nivel de base de datos (UNIQUE constraint)
- [ ] Revisión de código aprobada por al menos un integrante del equipo
- [ ] Sin vulnerabilidades OWASP críticas en el endpoint

#### US-002 — Registro y seguimiento de pedidos

**Como** Operador o Conductor  
**Quiero** registrar pedidos con dirección, ventana horaria y peso, y actualizar su estado a lo largo del reparto  
**Para** tener trazabilidad completa de cada entrega en tiempo real

**Criterios de aceptación (Gherkin / BDD):**

```gherkin
Escenario: Registro exitoso de pedido
  DADO que el Operador está autenticado y accede al módulo de pedidos
  CUANDO ingresa dirección de destino, ventana horaria y peso del paquete
  ENTONCES el sistema registra el pedido con ID único, lo vincula a la zona geográfica y lo deja disponible para asignación de ruta

Escenario: Confirmación de entrega por conductor
  DADO que el Conductor accede a su lista de pedidos asignados
  CUANDO marca un pedido como entregado exitosamente
  ENTONCES el sistema actualiza el estado a "Entregado" y registra la hora de confirmación

Escenario: Dirección fuera de cobertura
  DADO que se intenta registrar un pedido con dirección fuera del área operativa
  CUANDO el Operador envía el formulario
  ENTONCES el sistema rechaza el pedido y despliega: "La dirección indicada está fuera del área de cobertura operativa"
```

**DoD (Definition of Done):**
- [ ] Endpoint REST documentado en OpenAPI / Swagger
- [ ] Validación de zona geográfica implementada (cobertura Lima Este: SJL, El Agustino, Santa Anita, Ate)
- [ ] Estado del pedido persistido con timestamp de cada transición
- [ ] Pruebas unitarias con cobertura ≥ 80% sobre el servicio de pedidos
- [ ] Revisión de código aprobada por al menos un integrante del equipo

### EP-02 — Optimización de rutas sostenibles

---

#### US-004 — Generación de rutas optimizadas

**Como** Operador  
**Quiero** ejecutar la planificación diaria de rutas considerando ventanas de tiempo, capacidad vehicular y emisiones de CO₂  
**Para** maximizar la tasa de entregas a tiempo y minimizar el impacto ambiental de la flota

**Criterios de aceptación (Gherkin / BDD):**

```gherkin
Escenario: Generación exitosa de rutas para carga estándar
  DADO que el Operador tiene al menos un pedido pendiente y al menos un vehículo disponible
  CUANDO ejecuta la acción de generar rutas para el día operativo
  ENTONCES el sistema calcula y retorna rutas optimizadas para hasta 150 pedidos y 15 vehículos en tiempo máximo de 45 segundos (P95), respetando todas las ventanas de entrega

Escenario: Minimización de CO₂ como objetivo secundario
  DADO que el volumen de pedidos es menor a 150 y hay suficientes vehículos disponibles
  CUANDO el sistema ejecuta el algoritmo de optimización
  ENTONCES las rutas generadas minimizan las emisiones de CO₂ priorizando el cumplimiento de ventanas de tiempo

Escenario: Sin vehículos disponibles
  DADO que no hay vehículos disponibles en la flota activa
  CUANDO el Operador intenta generar rutas
  ENTONCES el sistema no ejecuta el algoritmo y despliega: "No hay vehículos disponibles para generar rutas en este momento"
```

**DoD (Definition of Done):**
- [ ] Algoritmo VRPTW/Green VRP integrado con OR-Tools o equivalente
- [ ] Tiempo de cómputo validado ≤ 45 s en P95 con dataset de 150 pedidos / 15 vehículos
- [ ] Función objetivo de CO₂ implementada como criterio secundario
- [ ] Pruebas de rendimiento documentadas con resultados
- [ ] Revisión de código aprobada por al menos un integrante del equipo

### EP-03 — Visibilidad operativa en tiempo real

---

#### US-005 — Visualización de rutas en mapa interactivo

**Como** Operador o Administrador  
**Quiero** ver en un mapa interactivo las rutas activas, la posición de vehículos y el estado de cada pedido  
**Para** supervisar la operación de reparto en tiempo real sin necesidad de llamadas telefónicas

**Criterios de aceptación (Gherkin / BDD):**

```gherkin
Escenario: Carga completa del mapa operativo
  DADO que el Operador accede al módulo de mapa y existen rutas generadas para el día
  CUANDO el mapa carga completamente
  ENTONCES el sistema muestra todas las rutas activas con paradas, estado de pedidos (pendiente / en camino / entregado) y posición actualizada de cada vehículo sobre cartografía de Lima Este

Escenario: Detalle de vehículo seleccionado
  DADO que el Operador selecciona un vehículo específico en el mapa
  CUANDO hace clic sobre el ícono del vehículo
  ENTONCES el sistema despliega panel lateral con ruta asignada, pedidos pendientes y tiempo estimado de arribo a la siguiente parada

Escenario: Fuente cartográfica no disponible
  DADO que OpenStreetMap / Leaflet no está disponible
  CUANDO el usuario accede al módulo de mapa
  ENTONCES el sistema despliega mensaje de indisponibilidad y ofrece la vista alternativa en lista de rutas
```

**DoD (Definition of Done):**
- [ ] Mapa implementado con Leaflet.js + OpenStreetMap
- [ ] Actualización de posición de vehículos en tiempo real (WebSocket o polling ≤ 10 s)
- [ ] Vista alternativa en lista funcional ante falla de mapa
- [ ] Pruebas de integración del módulo cartográfico
- [ ] Revisión de código aprobada por al menos un integrante del equipo

#### US-006 — Dashboard de indicadores operativos y ambientales

**Como** Administrador u Operador  
**Quiero** acceder a un panel de control con KPIs del día (pedidos entregados, tasa de cumplimiento, kilómetros y CO₂)  
**Para** tomar decisiones operativas y reportar avance ambiental en tiempo real

**Criterios de aceptación (Gherkin / BDD):**

```gherkin
Escenario: Carga del dashboard en horario operativo
  DADO que el Administrador accede al dashboard en horario operativo
  CUANDO el panel carga
  ENTONCES el sistema muestra en tiempo real: total de pedidos entregados vs. pendientes, porcentaje de cumplimiento de ventanas, kilómetros totales y toneladas de CO₂ emitidas en el día

Escenario: Filtro por distrito
  DADO que el Operador accede al dashboard con filtro por zona geográfica
  CUANDO aplica el filtro de distrito
  ENTONCES el sistema actualiza todos los indicadores mostrando únicamente datos del distrito seleccionado

Escenario: Sin datos del día actual
  DADO que no hay datos operativos del día (sin rutas generadas)
  CUANDO el usuario carga el dashboard
  ENTONCES el sistema muestra el panel con valores en cero e indica: "No se han generado rutas para la jornada actual"
```

**DoD (Definition of Done):**
- [ ] KPIs calculados a partir de datos reales de la base de datos
- [ ] Filtro por distrito implementado y funcional
- [ ] Actualización de datos en tiempo real (polling ≤ 30 s o WebSocket)
- [ ] Estado de cero datos manejado visualmente
- [ ] Pruebas de integración del módulo de dashboard
- [ ] Revisión de código aprobada por al menos un integrante del equipo

### EP-04 — Sostenibilidad y reportería ambiental

---

#### US-007 — Generación de reportes de sostenibilidad exportables

**Como** Administrador  
**Quiero** generar reportes exportables con métricas de CO₂, consumo de combustible y eficiencia de rutas por período  
**Para** cumplir con los compromisos ambientales de DistriRápido S.A.C. y la normativa ISO 14083

**Criterios de aceptación (Gherkin / BDD):**

```gherkin
Escenario: Generación exitosa de reporte de sostenibilidad
  DADO que el Administrador selecciona un rango de fechas y el tipo de reporte "Sostenibilidad"
  CUANDO ejecuta la generación del reporte
  ENTONCES el sistema procesa la solicitud en máximo 1.5 segundos (P95) y entrega un archivo exportable con métricas de CO₂ (kg), combustible (litros), kilómetros recorridos y entregas completadas en el período

Escenario: Exportación en formato CSV
  DADO que el Administrador genera el reporte en formato CSV
  CUANDO descarga el archivo
  ENTONCES el sistema entrega un CSV correctamente estructurado con encabezados en español y separadores compatibles

Escenario: Sin datos en el período seleccionado
  DADO que el rango de fechas no contiene datos registrados
  CUANDO el Administrador ejecuta la generación
  ENTONCES el sistema no genera un archivo vacío sino que despliega: "No se encontraron registros operativos para el período seleccionado"
```

**DoD (Definition of Done):**
- [ ] Generación de reporte en ≤ 1.5 s (P95) validada con pruebas de carga
- [ ] Exportación CSV estructurada con encabezados en español
- [ ] Cálculo de CO₂ alineado con metodología ISO 14083
- [ ] Manejo correcto del caso sin datos
- [ ] Revisión de código aprobada por al menos un integrante del equipo

### EP-05 — Calidad, seguridad y escalabilidad

---

#### EN-001 — Enabler: Infraestructura de seguridad OWASP y cumplimiento Ley N.° 29733

**Tipo:** Enabler técnico (Arquitectura / Seguridad)  
**Sprint objetivo:** Sprint 1 (base de toda la arquitectura)

**Descripción:**  
Implementar el middleware de seguridad que bloquee los vectores del OWASP Top 10 (especialmente inyección SQL, autenticación rota y exposición de datos sensibles), configure TLS 1.3 en todos los endpoints, y garantice la anonimización de logs de conductores y destinatarios conforme a la Ley N.° 29733.

**Criterios de validación:**

```gherkin
Escenario: Bloqueo de inyección SQL en endpoint de autenticación
  DADO que un atacante externo envía una cadena de inyección SQL al endpoint /auth/login
  CUANDO el API Gateway / WAF recibe la petición
  ENTONCES bloquea la petición, registra el evento en el log de auditoría y retorna HTTP 400 sin exponer detalles internos del sistema

Escenario: Anonimización de logs
  DADO que el sistema registra una operación que incluye datos personales de conductores o destinatarios
  CUANDO el evento se persiste en el log de auditoría
  ENTONCES los datos personales aparecen enmascarados conforme a los requisitos de la Ley N.° 29733
```

**DoD:**
- [ ] WAF / middleware de seguridad activo en todos los endpoints
- [ ] TLS 1.3 configurado y verificado
- [ ] Anonimización de logs implementada y probada
- [ ] Reporte de análisis OWASP Top 10 sin vulnerabilidades críticas
- [ ] Revisión de código aprobada por al menos un integrante del equipo

---

#### EN-002 — Enabler: Alta disponibilidad y failover automático (RTO ≤ 30 s)

**Tipo:** Enabler técnico (Infraestructura / Operaciones)  
**Sprint objetivo:** Sprint 2

**Descripción:**  
Configurar el clúster de contenedores con failover automático hacia zona de disponibilidad secundaria, de modo que ante la caída de un nodo primario el sistema restablezca el servicio en RTO ≤ 30 segundos y RPO ≤ 5 segundos, garantizando el SLA de 99.5 % en horario operativo 05:00 – 22:00.

**Criterios de validación:**

```gherkin
Escenario: Failover ante caída de nodo primario
  DADO que el nodo primario del clúster cae inesperadamente
  CUANDO el sistema de monitoreo detecta la indisponibilidad
  ENTONCES el failover automático restaura el servicio en la zona secundaria en un tiempo máximo de 30 segundos sin intervención manual

Escenario: Pérdida de datos ante failover
  DADO que ocurre un failover durante una operación de escritura activa
  CUANDO el servicio se restaura en la zona secundaria
  ENTONCES la pérdida máxima de datos no supera los 5 segundos de transacciones (RPO ≤ 5 s)
```

**DoD:**
- [ ] Clúster configurado con zona de disponibilidad secundaria activa
- [ ] Failover probado y documentado con RTO ≤ 30 s y RPO ≤ 5 s
- [ ] SLA de 99.5 % validado en entorno de staging
- [ ] Redis configurado para persistencia de sesiones durante failover
- [ ] Revisión aprobada por al menos un integrante del equipo

---

#### EN-003 — Enabler: Escalabilidad horizontal a 1,000 pedidos / 50 vehículos

**Tipo:** Enabler técnico (Arquitectura)  
**Sprint objetivo:** Sprint 4

**Descripción:**  
Validar que la arquitectura de contenedores con auto-scaling soporte el incremento de carga a 1,000 pedidos diarios y 50 vehículos activos sin rediseño de arquitectura, manteniendo la degradación de rendimiento ≤ 20 % respecto al baseline de 150 pedidos / 15 vehículos.

**Criterios de validación:**

```gherkin
Escenario: Rendimiento bajo carga escalada
  DADO que el sistema opera con 1,000 pedidos activos y 50 vehículos
  CUANDO se ejecuta la generación de rutas
  ENTONCES el tiempo de respuesta no supera 1.2 veces el tiempo baseline medido con 150 pedidos / 15 vehículos (degradación ≤ 20%)

Escenario: Auto-scaling ante pico de carga
  DADO que la carga del sistema supera el 70% de la capacidad nominal
  CUANDO el orquestador de contenedores detecta el umbral
  ENTONCES escala horizontalmente levantando instancias adicionales sin interrupción del servicio activo
```

**DoD:**
- [ ] Pruebas de carga documentadas con resultados a 150 y 1,000 pedidos
- [ ] Auto-scaling configurado y validado en entorno de staging
- [ ] Degradación de rendimiento ≤ 20 % confirmada
- [ ] Revisión aprobada por al menos un integrante del equipo
